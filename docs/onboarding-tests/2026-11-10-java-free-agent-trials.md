## 方法

### 誰が、何を読んで実行したか

- ワークフローのスクリプトが起動した独立したエージェントが、1試行につき1体、「このプラグインを入れた Claude Code」の役を演じました。3つの経路は並行して実行しました。試行の報告にモデルの識別子が記録されていないため、ここにはモデル名を書いていません。
- エージェントは、ユーザーのプロンプトごとに対応するスキルのファイルを読み直し、書かれている手順を文字どおりに実行しました。プロンプト1は `skills/define-contract/SKILL.md`、プロンプト2は `skills/generate-code/SKILL.md`、プロンプト3は `skills/generate-tests/SKILL.md` です。
- 読んでよいファイルは、その `SKILL.md` と、`SKILL.md` が名指しした `references/` のファイルだけです。`README.md`、`examples/`、`design/`、`eval/`、`docs/`、他のスキルは読まない設定でした。スキルの文面に無い知識に頼らないようにするためです。
- 文面が曖昧・誤り・指示なしだった箇所は、すべて「引っかかり」として重大度（blocker / major / minor）つきで報告させました。重大度はエージェント自身の判定です。

### ユーザー役（台本）

ユーザー役は「形式手法を使ったことのない開発者」で、答えは次の台本だけから返しました。台本に無い質問には「おまかせします（推奨の既定値で）」と答えます。

- 必要な操作：タスク作成、ステータス変更、削除、一覧取得
- ID：1から自動採番。削除したIDは再利用しない
- ステータスの変更：どの状態からどの状態へも変更してよい
- 単独のエージェントで、他のエージェントとの通信は無い
- 対象言語は TypeScript、出力先はカレントディレクトリ
- 今日は Java をインストールしない

## ラウンド1で見つかったこと

ラウンド1は3試行とも成功しましたが、**スキルの文面が十分だったから成功したのではありません**。3体のエージェントはいずれも、スキルの例をそのまま写さず自分の VDM-SL の知識で仕様を書いたこと、指示が無いのに自分の判断で仕様をファイルに保存したことを報告しています。文面どおりに従う実行では失敗しうる、という報告です。

major と判定された項目（3試行で計8件、内容としては次の5つ）：

1. **`define-contract` の VDM-SL の例が、VDM-SL として正しくなかった**（3試行すべてが指摘）。`types` / `functions` の見出しが無い、型定義と別の行に書かれた不変式、`pre f(x) == ...` の形、カリー化されたシグネチャ、存在しない演算子など。Java が無い環境では仕様を確かめる手段が無いので、例を写した仕様は、後で検証を実行した日に初めて失敗します。修正を担当したエージェントが作者のローカルの VDMJ 4.7.0 で確かめたところ、ステップ4のモジュール例と CRUD のテンプレートは構文エラーになりました。
2. **CRUD のテンプレートが ID を「最大のID + 1」で発行していた**。最新のタスクを削除した直後に同じ ID が再発行され、ユーザーの「削除したIDは再利用しない」に反します。また、状態を関数の引数で引き回す書き方で、`generate-code` が `state` と操作をクラスに変換する規則と噛み合っていませんでした。
3. **仕様をファイルに保存する指示が無かった**。ファイル名も保存先も完了報告もありません。チャットに表示するだけの実行では、次の `generate-code` が読むファイルがありません。
4. **聞き取りが長く、専門用語で行われた**。記録された質問は t1 で13問、t2 で15問、t3 で9問。依頼文に答えが書いてあることも尋ね、「不変式」「ステートレスかステートフルか」「サイドエフェクト」といった言葉を使います。その一方で、実際に決める必要があったことのうち、同じタイトルの可否と文字数の数え方はどの試行でも尋ねられませんでした。作成直後のステータスと一覧の並び順は、t3 では尋ねられましたが、t1 と t2 では尋ねられないまま既定値で決められていました。
5. **既存プロジェクトで、型チェックの報告が誤った安心を与えうる**（t3）。`generate-code` の完了報告は「プロジェクト自身の型チェックコマンド」を書くよう求めますが、`tsconfig.json` が `include: ["src"]` のとき、`npx tsc --noEmit` は `generated/` を1ファイルも読まずに終了コード0で終わります。

minor と判定された項目は3試行で計40件です。主なもの：通信が無いのに設計文書（PROTOCOL.md / API-SIGNATURES.md）を作るかのように読める記述、契約定義の次に `generate-code` を飛ばして `generate-tests` を案内する記述、生成ファイル名の規則が無いこと、`x~`（操作前の値）や構造的な等値比較の変換規則が無いこと、`VDM_CONTRACT_CHECK=off` が何を止めるのかの説明のばらつき、状態を持つ操作のテストの型が無いこと、完了報告に契約違反の例を見せる行が無いこと。

## ラウンド間でスキルに加えた変更

修正を担当したエージェントは、報告された引っかかりのうち26件に対応し、10件を理由つきで見送りました。変更したのは3つのスキルの `SKILL.md` と、それぞれの `references/` の1ファイルずつ、計6ファイルです。変更の全体は [CHANGELOG](../../CHANGELOG.md) の Unreleased にあります。ここでは試行の結果に関係する主なものを挙げます。

`define-contract`：

- `SKILL.md` と `references/contract-templates.md` の VDM-SL の例をすべて書き直し。書き直した例は、修正担当のエージェントが Markdown から取り出して VDMJ 4.7.0 の構文チェック・型チェックにかけ、通ることを確かめています（証明責務の証明まではしていません）。VDMJ がエラーにする書き方の一覧を「VDM-SL の書き方（必ず守る）」として追加
- CRUD のテンプレートを `state` と操作の形にし、次に発行する ID のカウンタで採番（削除した ID を再利用しない）
- 仕様を `<モジュール名>.vdmsl` として必ず保存（既定はカレントディレクトリ）し、最後に完了報告を必ず出す。報告には、指示が無く既定値で決めた項目（「決めたこと」）と、「構文チェック・型チェックを含め機械検証はしていない」ことを書く
- 「進め方の原則」を追加：まず依頼文を読み、足りないものだけを、平易な言葉で、推奨の既定値つきで、1回にまとめて尋ねる
- 設計文書（PROTOCOL.md / API-SIGNATURES.md）は、エージェント間の通信がある場合だけ作る
- 次の案内を「コード生成 → 契約テスト生成」の順に変更
- 本体を書かない定義は `generate-code` で TODO スタブになりテストが失敗するので、振る舞いが決まっているものは本体まで書く

`generate-code`：

- ファイルを書く前にプロジェクトの慣習（`package.json`、`tsconfig.json`、既存の `.ts` の import の書き方）を読むステップを追加
- 完了報告の型チェックの項目：コマンドが `generated/` を実際に読むことを確かめてから書く。読まないコマンドの終了コードを、生成コードのチェック結果として報告しない
- ファイル名（モジュール名の kebab-case）とクラス名（状態の名前）の規則、`VDM_CONTRACT_CHECK` の規則の一本化、仕様との表現上の差異を書く場所、完了報告に呼び出し例（正常な呼び出しと、契約に違反する呼び出し）を追加
- `references/typescript-rules.md` に、操作前の値のスナップショット、構造的な等値比較、TypeScript 6.0.3 での型チェックの実測などを追加

`generate-tests`：

- 状態を持つ操作のテストの型（戦略 F）、条項とテストの対応を毎回数える手順（3c）を追加
- 完了報告に「生成しなかったテスト」「対応する実装なし」「契約違反の例」の行を追加。既存のランナーを使う場合も、報告の前に自分で実行する
- 既存プロジェクトでのテストファイルの置き場所の決め方、Vitest の最小構成が作るファイル（`package-lock.json`、`node_modules/`）の明記
- `references/test-templates.md` の VDM-SL の入力例を正しい記法に修正

見送った10件の主なもの：スキル内の VDM-SL の例を自動で検査する lint（修正担当が編集できる範囲の外だったため。この修正の時点では、例の確認は手作業の1回だけで、そのログは残っていません。この lint は同じ日に別の作業で `npm run check:vdmsl` として追加されましたが、追加時点の実行では失敗するブロックがあり、全体は通りませんでした。[CONTRIBUTING.md](../../CONTRIBUTING.md) を参照）、`generate-tests` の約1,000行の構成の見直し、テストテンプレートの出力例の全面的な書き直し、Python 向けの規則（試行していないため）、README とサイトの同期（その担当の範囲外だったため）。

> **2026-11-11 追記**：上の「追加時点の実行では失敗するブロックがあり、全体は通りませんでした」は、2026-11-10 の時点の状態です。その後、失敗していた例は、正しい VDM-SL に直すか、単独では検査できないことを示すマーカー（検査しない、または構文だけ検査する）を付けました。2026-11-11 の実行では、検査の対象になったブロックはすべて通っています（[ログ](2026-11-11-check-vdmsl.txt)）。この検査は構文チェックと型チェックだけで、通ったことは「VDMJ が構文解析と型チェックを終えた」という意味です。マーカーで対象から外したブロックと、断片として検査しないブロックがあることも、ログに出ています。

なお、`generate-tests` のステップ0（既存のランナーを検出し、無ければ1回だけ実行方法を尋ねる）と、`generate-code` の完了報告は、ラウンド1より前に入れた変更です。ラウンド1はその状態のスキルで実行しました。

ラウンド2で報告された引っかかりは3試行で計41件、すべて minor の判定です（試行の手続きに関するものを含みます）。**この記録を書いた時点では、どれも未修正です。** 内容でまとめると次のとおりです。

> **2026-11-11 追記**：この記録を書いた後、下の項目の一部についてスキルの文面を変更し、同じ3つの経路をラウンド3としてやり直しました。どの項目が変わり、何が残っているかは [2026-11-11 の記録](2026-11-11-round3-and-verify-spec.md)にあります。その後さらに直した文面でのやり直し（ラウンド4）も、同じ記録に追記しています。下の一覧は、2026-11-10 に書いた時点の内容のまま残しています。

**絞り込みコマンドが、何も実行せずに成功したように見える**（t1 と t2 で実測）

- `generate-tests` の完了報告には「このテストだけを実行」するコマンドを書く行がありますが、Vitest の `-t` も `node:test` の `--test-name-pattern` も正規表現です。契約の条項から付けたテスト名には括弧が入るので、そのまま渡すと1件も一致しません。
- 実測：Vitest では `npm test -- -t "deleteTask(id) precondition"` が「59件スキップ」で終了コード0。`node:test` では、どのテストにも一致しないのに `tests 1 / pass 1`（ファイル単位の1件）で終了コード0。
- スキルは、これが正規表現であることも、報告に書く前に絞り込みコマンドを実行して確かめることも求めていません。

**契約違反を、ユーザーが自分の目で見る手段が弱い**

- 絞り込みコマンドの出力は成功・スキップの件数だけで、`ContractError` のメッセージは表示されません。
- 既存の Jest（CommonJS）プロジェクトでは、エラーを表示させる動くコマンドがスキルのどこにもありません。t3 のエージェントは `tsc` で一時ディレクトリにコンパイルする方法を自分で考える必要があり、「major に近い」と報告しています。
- 空のディレクトリでも、`generate-code` の完了報告にある呼び出し例を実行する方法は、後の `generate-tests` にしか書かれていません。

**`define-contract`：何を尋ねるかが実行ごとに変わりうる**

- 1回の質問に入るのは4項目までですが、決め忘れやすい項目は6つ以上あり、優先順位がありません。
- 「どの操作を用意するか」（依頼文の「更新」が何を変えるのか）が確認項目に入っていません。今回は3体とも自分の判断で尋ねました。
- ステータス変更の制限について、推奨の既定値が書かれていません（テンプレートには制限つきの例が入っています）。
