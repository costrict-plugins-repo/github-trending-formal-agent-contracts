## 0:15–1:00 ｜ S2 問題提起

> 複数のエージェントを並列で走らせている方、こういう経験ないでしょうか。エージェントAが作ったAPIを、Bが微妙に違うシグネチャで呼ぶ。CLAUDE.md に書いたはずの規約が、タスクの受け渡しのたびに少しずつ薄れていく。
>
> これ、今年の論文で "constraint drift" という名前がつきました。「制約は主張しただけでは維持されない」。プロンプトに書いた約束は、機械的には何も担保されていないんです。

**ポイント**: 「あるある」で頷かせるパート。論文名は読まない（スライドに任せる）。

---

## 1:00–1:45 ｜ S3 仕様駆動開発の現在地

> で、この1年で仕様駆動開発——Kiro、Spec Kit、cc-sdd——が来て、「仕様を先に書く」文化は定着しつつあります。これは本当に良いことです。
>
> ただ、spec.md は散文なんですよね。人間も読める、エージェントも読める。でも「実装がこの仕様を満たしているか」を機械はチェックできない。判定しているのは結局、LLM の自己申告と、人間のレビューです。

**ポイント**: SDD を dis らない。「半分解決した、残り半分の話をする」というスタンス。

---

## 1:45–2:30 ｜ S4 提案

> そこで提案です。エージェント間の契約を、形式仕様で書く。VDM-SL という ISO 標準の言語です。型不変条件・事前条件・事後条件を機械が判定できる形で書けて、VDMJ というツールが型チェックと証明責務の生成を、Z3 が翻訳した命題の判定（反例候補の探索）をやってくれます。
>
> 「形式手法って難しいんでしょ」と思いますよね。書くのは Claude です。人間は日本語で要件を言うだけ。

**ポイント**: 最後の一文がこの LT のコアメッセージ。ゆっくり言う。

---

## 2:30–3:45 ｜ S5–S7 デモ3連発

> （S5）実際の例です。スライド用に少し簡略化していますが、日本語でこれだけ言うと——「Done になったタスクは戻せない」「タイトルは100文字以内」——下の VDM-SL が出てきます。不変条件と遷移ルールが、そのまま形式になっているのが見えると思います。構文エラーが出たら Claude 自身が直します。自動修正できない場合は、未解決事項とログを示してレビューします。
>
> （S6）これを「検証して」と言うと、VDMJ が型チェックをして、証明責務を37個生成します。大変そうに聞こえますが、この証明責務は QuickCheck にかけて反例を探せます（QuickCheck は VDMJ の別のコマンドです。verify-spec は報告の後にその実行を提案します。確かめたのは、エージェントによる模擬試行の1回だけです。検査の手順への組込みは予定です）。人間の出番は反例が出たときだけ。たとえば、事後条件に off-by-one をわざと仕込んで QuickCheck にかけると——コードを1行も書く前に、具体的な反例つきで返ってきます。これが LLM の「たぶん大丈夫です」じゃなくて、チェッカーの判定だということです。
>
> （S7）最後に、この契約から Vitest のテストが自動生成されます。「Done から Todo に戻したら ContractError」。生成される TypeScript にはランタイム契約チェックが埋まっているので、別のエージェントが契約を破るコードを書いた瞬間、テストが落ちて止まります。

**ポイント**: ライブデモはしない（LTで死ぬ）。スライドの出力例を指差しながら話す。
S6 の反例パートが山場。「わざと仕込むと」の一言が、聴衆の「仕様自体が間違っていたら？」への回答になっている。時間が押していたら成功ケース（FAILED 0）の説明を短縮し、反例の話は残す。

## 3:45–4:35 ｜ S8–S9 意味づけ

> （S8）t_wada さんが対談で「AIエージェント時代に TDD はガードレールになる」という話をされていますが、その延長線上です。テストは書いたケースを守る。形式契約は宣言した性質の整合性を守る。しかも契約という1つのソースから、型もテストもランタイムチェックも生成されるので、エージェントが増えるほど効いてきます。
>
> （S9）ちなみに VDM、日本と縁が深くて、おサイフケータイやモバイル Suica に載っているモバイル FeliCa IC チップのファームウェア仕様は VDM++ で書かれています。スマホで改札を通るたび、形式手法が動いてるんですね。そして現時点で、私の調べた限り、VDM と AI エージェントを繋いだ公開ツールはこれ1つです。

**ポイント**: FeliCa は笑いどころ兼つかみ。「調べた限り」を必ず添える（断定しない）。

## 4:35–5:00 ｜ S10 CTA

> コミュニティマーケットプレースに載っているので、この2行で入ります。入れたら、スライドの3つを順に打つだけ。契約の定義、TypeScript コードの生成、契約テストの生成です。ここまで Java は要りません（VDMJ での検証は Java を入れてから）。既存リポジトリなら「このコードから仕様を抽出して」でも動きます。今夜ぜひ。形式手法×AIコーディング、日本からやっていきましょう。ありがとうございました。

| 質問 | 回答の骨子 | スライド |
|---|---|---|
| Outcomes と何が違う？ | 確率的なLLM採点 vs 構文・型検査と翻訳した論理式の判定（翻訳範囲に限る）。併用可 | A3 |
| VDM-SL 読めない人はレビューできない？ | export-human-spec で自然言語仕様書を生成 | A3 |
| 学習コスト高くない？ | 書くのはClaude。POの解説も日本語でさせられる | A3 |
| 効果はあるの？ | 同梱 eval は探索的で対照群に意図的欠落がある。導入効果の証拠にはしない。根拠は examples/task-manager/evidence/ | A2 |
| 全15スキルの構成は？ | フォワード（DBスキーマ導出・モデル配分を含む）/リバース/入出力の3系統 + 参照 | A1 |
| TLA+/Dafny じゃだめなの？ | 用途が違う（TLA+=並行系設計、Dafny=検証済み単体コード）。エージェント間のデータ契約にはVDMが合う。日本語資産も豊富 | 口頭 |
| ツールチェーン重くない？ | 契約定義→コード生成→契約テスト生成は Java 不要で、Node.js で動く（既存のテストランナーがあればそれに合わせ、無ければ Vitest の最小構成か Node.js 組み込みランナーを選ぶ）。フル検証は Java 11+ + VDMJ（zip 展開のみ）+ Z3（pip） | 口頭 |
| 仕様自体が間違っていたら？ | 矛盾はPO検証で反例として出る（S6）。仕様の妥当性はexport-human-specの日本語仕様書を人間がレビュー | S6/A3 |
