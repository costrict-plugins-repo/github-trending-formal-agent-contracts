## ラウンド3で報告された引っかかり

3試行で計17件、すべて minor の判定です（t1 が6件、t2 が7件、t3 が4件）。内容でまとめると次のとおりです。

**`define-contract`**

- 依頼文の「更新」が何を変えるのか（タイトルか、ステータスか、両方か）を尋ねる指示はありますが、その質問に付ける推奨の既定値が書かれていません（t1、t2）。今回は2体とも、自分の判断で「ステータスの変更のみ」を推奨にしました。ここで決まることは、その後に生成されるものすべての公開 API を左右します。
- 依頼文が他のエージェントに触れていないとき、どう扱うかが書かれていません（t1、t2）。2体とも、尋ねずに単独のエージェントとして扱いました。台本にあった答えは使われませんでした。
- 完了報告の例は操作を `deleteTask(id)`（camelCase）と書いていますが、仕様とテンプレートでは `DeleteTask`（PascalCase）です。どちらで書くかの指示が無く、3体とも仕様の名前で書きました（t1、t2、t3）。利用者は、次の `generate-code` の報告で初めて、実際に呼ぶ名前（`deleteTask`）を見ることになります。操作の英語名を黙って決めている点（上の `UpdateStatus` と `ChangeStatus`）も、「決めたこと」の一覧には入りません（t3）。

**`generate-code`**

- 操作の引数の型が、不変式つきの型の別名（`Title`）や引用型（`TaskStatus`）である場合に、どこで何を検査するかの規則がありません（t1、t3）。仕様の `CreateTask` には事前条件が無いのに、101文字のタイトルが「Pre-condition failed」と報告される、`VDM_CONTRACT_CHECK=off` では同じ入力のメッセージが変わる、という前回の指摘は残っています。
- 変換例の `invTitle` は、値が文字列かどうかを確かめずに長さを読みます。型の違う値（`undefined` など）を渡すと、`ContractError` ではなく `TypeError` になります（t2 が実測）。この場合を確かめるテストは生成されないので、テストは通ります。

**`generate-tests`**

- 条項の数え方（3c）は「いちばん外側の `and` で分ける」ですが、限量子（`forall`）の本体の中の `and` をどう数えるかが書かれていません（t1、t2、t3）。今回は3体とも1つと数えて 17/17 と報告しましたが、3体とも、18/18 と数える読み方もできると指摘しています。
- 完了報告の「契約違反の例」の行は、呼び出し・メッセージ・絞り込みコマンド・表示用のコマンドが1つの箇条書きに入り、埋めると450文字ほどの1行になります（t1）。
- `node:test` では「このテストだけを実行」が1件に絞れないことがあります（t2。上の表）。
- Node.js 組み込みのテストランナーを選ぶと、テストファイルの先頭に実行ディレクトリをコメントで書きますが、絶対パスで書くかどうかの指示が無く、そのマシンだけで通じる絶対パスが書かれました（t2）。
- 既存の CommonJS のプロジェクトで、契約違反を表示する手段がありません（t3。上の節）。同じ箇所で、メッセージの文面まで確かめるテストが通ったことを「実行して確認」と数えてよいかどうかも書かれていません。
